Title: Proposal: song/pattern tuning, project chip curves and multi-subsong NSF import

Hi BleuBleu and the FamiStudio team,

I enjoy using FamiStudio for chiptune composition. Project-level reference tuning is useful, and I would like to discuss extending it to individual songs and timeline pattern columns, with optional project-wide per-chip corrections for individual notes.

There is a working local prototype based on 4.5.3. Its core behavior is:
- Project reference -> song override -> pattern-column override.
- An A4 reference plus twelve pitch-class offsets in cents, repeated across octaves.
- A separate project-global curve with 96 independently adjustable absolute integer hardware values per chip. Graph dragging uses the FamiStudio default +/-50; manual entry can exceed that band within the selected hardware representation's limits. VRC7 retains the note's default block, using F-number 1..511 for block 0 or 256..511 for higher blocks. The complete 96-key horizontal keyboard reuses the piano roll's native rendering, with zoom/scroll and small arpeggio-like blocks. Their -50/0/+50 axis is relative to each note's default, so the unchanged curve is flat; labels show absolute hardware values. Values entered beyond the band remain exact, while their drawn blocks clip at the edge.
- Chip-specific quantization, including FM block/f-number selection.
- Playback and FamiStudio engine/NSF export consume the same tuning tables.
- Existing property dialogs receive additional controls; no extra song/pattern tabs.
- All seven existing UI languages have strings for the additions.
- NSF/NSFe import can select several subsongs from one file, each with its own capture duration, and combine them safely in one project. Duplicate resource names no longer imply identical data. Cancellation discards the batch. This remains register capture, rather than reconstructing a game's original instruments or command stream.

The engine extension is optional (FAMISTUDIO_USE_CUSTOM_TUNING). The fork uses stream instruction $5f with period-low, period-high and fractional-bit table pointers and resets them on song initialization. The new project curves reuse that existing fork instruction; they need no additional assembly or bundled-driver changes. The local tests compare NSF CPU-emulated pitch registers with editor output and verify held notes, slides, vibrato, loops and track switching. Earlier checks found that the four single-expansion assembler variants generate identical bytes over 32 configurations and the ten upstream register-trace fixtures still match; the engine/native code is unchanged in this revision.

Curve values and their reference-Hz/clock/N163-channel-count basis are stored exactly as integers through binary files, text interchange and undo. The curve is not cents-based: timer/period chips expose their actual values, N163/FDS expose frequency words, and VRC7 exposes F-number at the displayed default block. VRC6 saw and EPSM FM follow the pitch derived from their chip's canonical pulse/PSG curve. Song/pattern reference ratios and the existing twelve-note cents temperament still apply before final hardware quantization. Default/reset curves preserve existing behavior. Because curves are intentionally global, importing songs with conflicting active-chip curves is rejected rather than silently retuning them; an empty destination adopts the incoming curve. The multi-subsong importer is independent enough to review separately from tuning.

There is also a separate, larger desktop experiment: per-song channel stereo/pan during playback, and a quantity beside each enabled expansion checkbox for additional copies of that chip. Extra copies are restricted to the editor/playback/audio outputs; hardware exports reject them. I understand this may be outside the intended hardware model and would be happy to keep it as a fork-only feature.

The curve editor reuses the mobile property/input infrastructure and includes touch selection, long-press/double-tap entry and pinch zoom as preparation for future mobile integration. The Android toolchain is unavailable locally; Android compilation, rebuilt native libraries and device behavior still require validation before an Android release.

Would you be interested in reviewing the tuning portion or the smaller multi-subsong import change first? Before proposing a PR, I would appreciate guidance on the desired UI, project-format versioning, stream opcode, memory budget, and whether twelve-note temperament and per-chip note curves fit the intended scope. The prototype saves a deliberately separate project-format version (1002), while reading the previous fork format 1001 and official formats through 19. This would need to follow the versioning approach you prefer for an upstream contribution.

The Windows build is tested locally: 1,506 existing regression assertions, 1,886 chip-curve assertions and 39 multiple-import assertions pass, totaling 3,431. The new checks include exact requested hardware values at all 96 notes for all eight chips in both regions. All seven UI languages render, and the Chinese interaction checks also pass at 150% scaling. Another 29 touch-event assertions pass in the desktop harness at both 100% and 150%; this is shared-event evidence, not Android device validation. A small NROM cartridge from the previous revision boots the modified engine in an independent FCEUmm emulator, with captured audio verifying song/pattern reference changes, a cents offset and loop restoration. Physical hardware verification remains outstanding. The latest Linux and macOS C# builds have zero errors, and a common CMake native build plus a three-OS CI configuration are included; actual Linux/macOS runtime testing and remote CI runs remain outstanding. Android is not validated. I can provide focused changes and original reproduction projects after we agree on scope.

Any separate, local game-specific conversion work is outside this application's import features. Public source packages and test fixtures exclude newly extracted Gimmick! ROM/music/instrument data and newly derived projects; already tracked upstream demo songs remain unchanged.

Thanks for FamiStudio and for considering the proposal.
