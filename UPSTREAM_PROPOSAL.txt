ENGLISH — suggested issue or discussion text
============================================

Title: Proposal: optional per-song/pattern tuning and independently reviewable
       editor, noise-instrument and playback improvements

Hi! I use FamiStudio for 8-bit composition and have built an experimental desktop
fork from 4.5.3. The initial need was to give songs and pattern columns their own
A4 reference and twelve-note temperament, while preserving those choices in the
sound engine and NSF export. That work also produced several independent editor
and playback improvements. Would any of the following be useful upstream?

I am not asking you to adopt a large combined patch. I would like to agree on the
useful scope first, then prepare small PRs against your current branch, using your
preferred format versions, opcodes, naming and UI conventions. Features outside
FamiStudio's intended scope can stay in the fork.

Suggested review units
----------------------
1. Save safety and discoverability. A visible Save As command complements the
   existing shortcut/context menu. Saves finish a sibling temporary file before
   replacing the destination, and a failed save cannot continue a pending close
   or project replacement. The importer change can be another small PR: select
   several NSF/NSFe subsongs, retain individual capture durations, merge resource
   identities safely, and return no partial project after cancellation/failure.

2. Tuning. Optional project -> song -> pattern-column inheritance for A4 and
   twelve cents offsets, plus separate project-global integer per-chip curves.
   Playback, preview and export share one quantization path. The UI extends the
   existing property pages; the curve editor uses the native piano style. Engine
   support is optional and supplies table pointers rather than baking every frame.
   The canonical hardware ranges and the choice to store reference bases deserve
   review before settling an upstream representation.

3. Editable hardware articulation. The three noise macros expose hardware period,
   envelope control and restart. A default-off follow-note mode transposes the
   period macro relative to C4 across the 16 hardware indices. Software envelope
   decay, full seven-bit DPCM mapping DAC, APU attack-phase reset, low-byte pitch
   saturation and hardware sweep can be reviewed separately. Old projects keep
   their old defaults; synthetic register/CPU tests cover the new behavior.

4. Sequence semantics. Pattern playback delay and a same-channel loop-variant
   reference preserve readable scores whose first pass and repeated body differ.
   Engine export compiles these to ordinary note/effect streams. Their ownership,
   loop-boundary behavior, legacy-export guards and UI need an independent review.

5. Independent update clocks. Project output can use 1x/2x/4x, while existing
   songs and envelopes keep their authored clocks and actual speed. Native audio
   distributes calls uniformly inside a physical frame. NSF/NSFe periods match;
   games provide their own evenly spaced timer/IRQ calls. The engine feature is
   optional and absent from default builds. Existing song grids are not silently
   resampled; exact envelope-rate conversion is offered separately. Unsupported
   cross-region and legacy-output cases report errors rather than change timing.

6. Desktop mixing and storage, if desired. Per-song live channel pan/stereo and
   repeated expansion copies are audio features, deliberately rejected where the
   hardware format cannot represent them. They may be inappropriate upstream and
   can remain separate. Lossless project compression is also separable from the
   musical features and need not dictate upstream's format policy.

Integration and maintenance
---------------------------
The C# model, serialization, playback, property controls and translations are
shared across desktop platforms. All seven current languages are covered. The
mobile toolbar/property-control paths are prepared, but desktop tests are not
proof of Android device support.

The fork uses private project format 1007 and a separate settings/clipboard
namespace. It reads old official projects and earlier fork versions; that is not
a proposal to reserve those numbers upstream. Matching music exports require the
fork engine. The optional assembly features default off; ROM/RAM/CPU costs should
be reviewed per feature, including the combined configurations and bundled menus.
CA65, ASM6, NESASM and SDAS sources and the CA65 multi-expansion engine are included.

Native libraries must be rebuilt for each platform. Earlier fork changes add
emulator-context/stereo functions and NesApuSetUpdateRateMultiplier; an upstream
binary with the old ABI is insufficient. NotSoFatso timing/sweep fixes require its
own rebuild. CMake entries and a three-OS CI configuration are provided. Local
Windows runtime evidence and Linux/macOS managed builds are distinct; target-OS
audio devices, packaging, signing/notarization and Android remain to be validated.

Tests and review evidence
-------------------------
Original synthetic tests exercise binary/text/undo/clipboard compatibility,
numeric and dialog interactions, all-chip pitch registers, real NSF CPU execution,
envelope clocks, hardware articulation, repeated rendering and assembly parity.
Separate cartridge demonstrations execute in an independent emulator. Tests
distinguish frame-level editor behavior from cycle-timed CPU hardware behavior;
there is no claim of physical-console or universal-player validation.

Revision 8 passes 22 file-save checks, 597 noise-follow checks (96 real NSF CPU
executions), all seven UI languages at 100% and Chinese at 150%. The four
assemblers agree across 64 noise configurations, and 60 NES/FDS templates pass
31,956 layout checks. Logs and screenshots can accompany the corresponding PR.
The Windows account could not create symbolic links, so Unix/link semantics still
need target-platform runtime verification. Earlier revision reports remain
identified by their revision, not reused as current proof.
No newly extracted commercial-game ROM, sample, instrument, score or derived
project will be included in the public patch or synthetic fixtures. Existing
upstream examples and their licenses remain unchanged.

If this direction is useful, which review unit would you prefer first? I can
prepare that unit independently and adapt its API, UX and engine design before
bringing the remaining features forward.


中文 — 可直接用于讨论/意见的正文
================================

标题建议：可选的歌曲/样式调音，以及可分开审阅的编辑器、噪声乐器和播放改进

你好！我一直使用 FamiStudio 创作 8-bit 音乐，最近以 4.5.3 为基础做了一个
实验性桌面分支。最初的需求是让每首歌和时间轴每列样式有独立的 A4 标准音
及十二音级律制，并能正确导出到声音引擎和 NSF。开发中也整理了一些彼此
独立的编辑器和播放改进，想先了解其中哪些符合 FamiStudio 的发展方向。

我希望先商定范围，再针对你们当前的开发分支拆成小型 PR，遵循你们选择的
格式版本、指令、命名和界面习惯，不需要一次接收整个分支。不适合主项目的
功能可以继续留在独立分支中。

建议拆分顺序
------------
1. 保存与导入。显式“另存为”入口；完成临时文件后再替换目标；保存失败不
   继续关闭或切换工程。NSF/NSFe 多选子曲导入可再独立成一个 PR，涵盖各曲
   时长、资源身份、取消和失败时不留下部分导入结果。
2. 调音与曲线。项目→歌曲→样式继承的标准音和十二音级偏移，以及独立的
   工程级芯片整数曲线。播放/预览/出口共享量化；引擎通过可选表指针支持，
   不把每帧音高烘焙成事件。硬件表示边界和曲线基准的存储方式可先讨论。
3. 乐器表达能力。噪声周期、硬件包络控制和重启宏；默认关闭的 C4 相对跟随
   模式；软件包络衰减；完整七位 DPCM 初值；APU 起音相位、低字节饱和及
   硬件扫频。这些可以逐个提交，旧工程默认播放保持不变。
4. 曲式。样式播放延迟和同声部循环变奏，表达首次与重复演奏的真实差别。
   引擎仍导出普通音符/效果流，独立审查跨界事件归属、循环、旧出口与界面。
5. 独立时钟。输出 1×/2×/4×，已有歌曲和包络保留作者时基及真实速度；
   原生音频均匀分配子帧，NSF/NSFe 使用相应周期，游戏用计时器/IRQ 调度。
   引擎默认不开启，不自动扩大旧乐谱网格。包络时基转换要求能无损表达；
   暂不支持的跨制式/旧格式会明确报错。
6. 可选桌面功能。实时声像/立体声、重复扩展芯片仅用于音频，不强行写入
   无法表达的硬件格式。如果不符合主项目范围，可保留为分支功能。工程
   无损压缩也可单独讨论，不要求你们接受本分支的文件格式政策。

移植、兼容与证据
----------------
模型、序列化、播放器、属性页及七语言翻译由桌面平台共用，日常逻辑修复
可以共享；首次合入仍需审查原生 ABI、文件格式及引擎容量。移动端共享控件
已准备，但桌面触摸事件测试不能代表 Android 真机验证。

分支私用格式为 1007，设置及剪贴板命名独立，支持读取旧官方/分支工程。
这些版本号不是给上游预留的建议。新导出需要匹配的引擎；各可选功能默认
关闭，需分别审查 ROM、RAM、CPU 及组合配置。已提供四种汇编器和多扩展
CA65 版本。原生层包含模拟器实例/立体声接口及输出率接口，每个平台必须
重编，不能沿用旧 ABI 的动态库；NotSoFatso 的时序修复也需重编。

仓库提供原创合成测试、CMake 入口和三桌面平台 CI 配置。测试包括保存格式/
文本/撤销、实际界面交互、芯片寄存器、真实 NSF CPU 执行、包络时钟、重复
渲染和汇编器字节一致性，另有独立模拟器卡带示例。Windows 运行验证、
Linux/macOS 托管编译与目标平台原生验证严格分开。尚未测试物理 FC/NES，
也不宣称编辑器帧头写入与所有游戏 CPU 周期调度产生逐采样相同的声音。

R8 已通过 22 项保存、597 项噪声跟随（含 96 份 NSF 真实 CPU 执行）、七语言
100% 和中文 150% 界面检查，64 种配置四汇编器一致，60 个模板通过 31,956
项布局检查，可随相关 PR 提供日志与截图。本机无创建符号链接权限，Unix/
链接仍需目标平台运行验证；历史报告保留明确版本。新提取的商业游戏 ROM、
样本、乐器、曲谱及派生工程均不
进入公开源码或测试夹具，上游已存在的示例及其许可说明保留原样。

如果其中有适合的方向，你希望先审阅哪一部分？我可以先准备该部分的独立
变更，并根据反馈调整接口、界面和引擎设计。
